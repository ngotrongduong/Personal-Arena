## Goal (owner view)

Brains trained on the old game must not be thrown away: when the owner presses TRAIN, a v4 brain is upgraded to
v5 (bigger input, two more skill choices) and keeps learning. This task makes the trainer understand v5.

## Work

1. `Trainer/schemas/survivor_v5.json`, same format as `survivor_v4.json` (read `Trainer/arena_trainer.py`
   `load_schema`, `observation_size`, `column_map`, `action_map`). `schema_version` 5, `observation_size` 2592, field names
   for the new self fields, inventory `repeat` 128, offers with 130 fields per slot, branches `[9, 7, 5]`.
   The C# test `JsonSchemaMatchesTheCoreLayout` (in `CoreTests`, currently skipped because this file did not exist)
   checks the file against Core: make it pass for real, run `dotnet test CoreTests -c Release`
   (`export PATH=$PATH:/root/.dotnet`).
2. `arena_trainer.SCHEMA_VERSION = 5` and every place that assumes the current schema (champion, brain locator
   files, train_service, config YAMLs if they name sizes). New runs write `schema_version.txt` = 5.
3. `brain_upgrade.py`: upgrade v4 → v5 through the generic column/action mapping. New columns start at zero weight,
   the new skill choices (indices 5 and 6 of the skill branch) get a strongly negative bias so the old brain does not
   suddenly pick them while the mask is closed, existing weights keep their values (function-preserving upgrade for the
   unchanged inputs). Check how v3 → v4 was done and keep that behaviour. Chain v3 → v4 → v5 if the code supports chaining.
4. `export_brain.py` / `.brain` format: must write the v5 sizes (input 2592, branches 9/7/5). The C# loader
   `PolicyBrain` reads sizes from the file header: make sure nothing hardcodes 2264.
5. Tests (pytest): `test_export_brain.py` (2264 → 2592, branches), `test_brain_upgrade.py` (v4 → v5: shapes, mapping of
   old columns to new offsets as in the table, new columns zero, skill bias), schema loader, champion, train_service.
   The binary cross-language fixtures `CoreTests/Fixtures/brain_upgrade/{old.brain,new.brain,map.json}` are regenerated by
   the test with `PA_REGEN_FIXTURES=1` (see `test_cross_language_fixtures_are_current`); regenerate them for v4 → v5 and
   run the C# `PolicyBrainUpgradeTests` against them. Note the known issue: that fixture test fails on Linux because
   torch RNG bytes differ from the committed Windows-generated file; after regeneration on this machine it will pass
   here but could differ on the owner's PC; make the fixture generation independent of torch's RNG
   (e.g. build the fake checkpoint from `numpy.random.RandomState(seed)` with explicit float32 casts) so the committed bytes
   are the same on every platform, and say so in the Report.
